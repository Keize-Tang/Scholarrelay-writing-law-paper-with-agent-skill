# 14 · PDF 文献提取为文本（标准做法·决策记录）

> **本章的目的是"不要再重新决策"。**
>
> 历史上每开一个新任务窗口，AI 都要重新试一遍"这篇 PDF 怎么提取文本"——
> 试库、试参数、试到能用为止。这是纯粹的浪费：**它每次都会得出同一个结论。**
>
> 本章把结论固定下来。**默认直接用下面的命令，不要重新评估选型。**

---

## 一、标准做法（一条命令）

```bash
python scripts/pdf2txt.py 文献目录/
```

就这么简单。脚本会：

- 批量处理目录下所有 PDF
- 自动选用最快的引擎
- 按每页平均字符数**自动判定哪些是扫描版**（需 OCR）
- **跳过已提取且比 PDF 新的 txt**（增量，不重复劳动）
- 输出分页标记 `===== PAGE n =====`，便于精读时定位页码

### 常用变体

```bash
# 先只检查（不写文件）——看看哪些是扫描版、需要先做 OCR
python scripts/pdf2txt.py 文献目录/ --check

# 输出到单独目录，保持工作区整洁
python scripts/pdf2txt.py 文献目录/ --outdir 文献txt/

# 强制重新提取（默认增量跳过）
python scripts/pdf2txt.py 文献目录/ --force

# 不要分页标记（一般不需要，分页标记对接引注时定位页码很有用）
python scripts/pdf2txt.py 文献目录/ --no-pages
```

## 二、为什么是 PyMuPDF（实测数据，不必重测）

在**本机真实语料**上实测 8 篇知网文献（同目录、同时点、逐篇计时）：

| 引擎 | 耗时 | 总字符 | **非空白字符** | **汉字数** | 控制台噪声 |
|---|---|---|---|---|---|
| **PyMuPDF**（`pymupdf`） | **0.71 s** | 115 718 | 25 309 | 16 694 | 无 |
| pypdf | 8.47 s | 132 408 | 25 309 | 16 694 | **有**（`Multiple definitions in dictionary...`） |

**关键结论**：两者的**非空白字符数与汉字数完全一致**——
pypdf 多出来的 1.4 万字符**全部是空白符**，不是内容。所以：

- **内容无差别**（不用担心"哪个提取更全"）
- **PyMuPDF 快约 12 倍**（0.71s vs 8.47s）
- **PyMuPDF 不打印噪声警告**（pypdf 会把警告混进输出，干扰日志阅读）
- 全目录 55 篇 PDF：PyMuPDF **4 秒**跑完

因此：**优先 PyMuPDF，环境没有时自动回退 pypdf。** 脚本已实现自动选择。

### ⚠️ 一个导入名的坑

不要写 `import fitz`。PyMuPDF 1.28 起已弃用该名，会打印
`DeprecationWarning: The fitz API is deprecated...`。

**用 `import pymupdf`。** 脚本已按 `pymupdf` → `fitz` → `pypdf` 顺序自动尝试。

## 三、不要做的事（避免重复造轮子）

| ❌ 不要 | 原因 |
|---|---|
| 重新对比 pypdf / pdfplumber / pdfminer 的选型 | 已测过，结论固定，见上表 |
| 为每篇 PDF 单独写一个提取脚本 | 用 `pdf2txt.py`，它支持批量 |
| 每次重新决定输出文件名与目录结构 | 约定：与 PDF 同名、扩展名改 `.txt`，默认同目录 |
| 用 `import fitz` | 会打印弃用警告，且未来会失效 |
| 手动复制粘贴 PDF 文字 | 慢、丢格式、易漏段 |
| 为了让 AI"能读到"而把 PDF 转成图片 | 图像不能直接比对原文；正文核验要的是**可检索的文本** |
| 在正文里写"根据 PDF 第 12 页"却拿不到页码 | 用默认的分页标记定位 |

## 四、扫描版 PDF 怎么办

**判定标准**：每页平均字符数 < 80 → 判定为无文本层（扫描件）。
可用 `--min-per-page` 调整阈值。

真实例子：同一目录下 55 篇 PDF 中，`《中国劳动关系学院学报》稿约.pdf`
提取出 18 个字符、每页 18 字 → 判定为扫描件。其余 54 篇每页 1400—2100 字，正常。

**处理流程**：

1. 用 OCR 工具转换（`pdfkit-py` 的 OCR 功能，或其他 OCR 服务）；
2. 把结果保存为**与 PDF 同名的 `.txt`**，放进同一目录；
3. ⚠️ **OCR 结果必须人工抽查**——数字、年份、文献编号、页码最容易识别错；
4. 在文献精读笔记里注明"该文文本系 OCR 得到"，引用页码时留出 ±1 页误差的余地。

> 为什么强调第 3 步：OCR 常把「2024」识成「202A」、把「第 8 条」识成「第 8 奈」。
> 这类错误若进了正文，就是审稿人一眼可见的硬伤。

## 五、提取之后：怎么和精读衔接

文本提取只是手段，目的是支撑**引用前回读原文核验**（见 `05-writing-discipline.md`）。

```
PDF 下载（人）
   ↓  scripts/pdf2txt.py 目录/
同名 .txt（含 ===== PAGE n ===== 标记）
   ↓  逐篇精读
文献精读笔记（原句 + 页码 + 对本文的用途，见 references/04）
   ↓  写作时定向回读
正文引用（每处引用真实对应原文）
```

**两个提醒**：

1. **txt 中的 `PAGE n` 是 PDF 页序，不一定是刊物页码。**
   精读笔记里标注页码时必须写明是"PDF 页"还是"刊物页"，避免正文引注错位。
2. **txt 只是工作底本，不能当引文出处。**
   正文引用的页码应回到刊物实际页码（期刊论文的起止页码从知网题录取，
   见 `06-citation-and-validation.md`）。

## 六、环境依赖

`scripts/pdf2txt.py` 在**本机管理的 Python 3.13 环境中可直接运行**（已装 PyMuPDF 1.28.2），
**无需任何安装**。

若换到没有 PyMuPDF 的环境：

```bash
pip install pymupdf     # 推荐：快约 12 倍
pip install pypdf       # 备选：脚本会自动回退到它
```

> `md2docx.py` 需要 `python-docx`，其余脚本只用标准库或上述引擎。
> 不必为了 PDF 提取去装 pdfplumber、pdfminer.six 等——它们没有在本项目语料上表现出优势。
