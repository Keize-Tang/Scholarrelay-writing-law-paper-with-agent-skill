# 09 · 修订纪律：为什么有的论文越改越好，有的越改越烂

> 这一节是本工作流里**最贵的经验**，来自三次真实合作的对照。
> 交付物齐全（启动包、分级清单、精读笔记都做了）**并不能保证论文能写出来**。
> 决定成败的是修订方式，不是资料准备。

---

## 一、三次实战的对照

| | **A · 思想史论文**（评价：最好） | **B · 方法类论文**（评价：次之） | **C · 规范分析论文**（评价：放弃） |
|---|---|---|---|
| 文献准备 | 三轮需求，用户主导 | 题录解析 + 工具化 | 启动包 + 分级清单 + 精读笔记**全齐** |
| 迭代方式 | **整篇重写**，每版一个完整文件 | **整篇重写**（多版生成器） | **字符串替换打补丁** |
| 修订脚本 | 0 个 `fix_*` | 0 个 `fix_*` | **7 个 `fix_*.py`** |
| 方法自检 | 有（逐篇统计文本用例） | 有（主题一致性诊断） | 无 |
| 证据纪律 | 边写边核 | **发现引了未读原著 → 直接删引用** | 无独立审稿报告落盘 |
| 版本字数曲线 | 6.1k → 7.3k → 7.6k → 8.8k → 8.6k | 平稳 | 9.9k → 12.7k → 13.7k → **5.8k** ⚠️ |
| 结局 | 定稿 | 定稿并自审 | 拦腰砍断后放弃 |

**注意 C 的悖论**：它的资料准备是三次里最完备的——写作启动包写了 180 行，
文献分 A/B/C 三档共 25 篇精读，还专门做了取证清单。**但这些都没有救它。**

---

## 二、病根：补丁式迭代

C 项目的修订脚本清单（全部是对同一个 md 文件做字符串替换）：

```
fix_long.py          ← 拆长句
fix_long2.py         ← 继续拆长句
fix_review.py        ← 按"审稿意见"逐条替换
fix_round3.py        ← 第三轮替换
fix_sec44.py         ← 重写一个小节
fix_v5.py            ← v5 版替换
fix_v6_chegulun.py   ← "v6 车轱辘话清除：11 处修订"
```

而 A 项目的脚本只有两个：一个用于提取 PDF 文本，一个用于排版生成 Word。**没有任何修订脚本。**

### 为什么打补丁必然失败

1. **补丁只能改句子，改不了结构。** 当问题是"第三章的论证链条不成立"，逐句替换是无效劳动。
2. **补丁会累积冗余。** 每加一句解释，就和上一句重复一点；补到第十轮，就成了"车轱辘话"。
   这就是为什么最后要专门写一个脚本去清除冗余——**冗余是补丁生产的，不是写出来的。**
3. **补丁不可见全局。** 你在替换第 400 行的句子时，看不到第 1200 行已经说过同样的话。
4. **越补越长，然后被迫暴跌。** C 项目从 9.9k 涨到 13.7k，超了目标字数，
   于是粗暴砍到 5.8k（跌 57%），结构随之瓦解。

### 正确做法

> **每一轮修订都产出一个人工审阅过的完整新版本文件，编号递增。**
>
> `论文正文_XX_v3.md` → 通读 → 整段/整章重写 → `论文正文_XX_v4.md`
>
> 不要写脚本去 `replace(old, new)` 地改正文。脚本只用于：题录解析、编号重排、格式转换。
> **凡是改动"人说的话"的，都必须由人/AI 重写，不能由脚本替换。**

## 三、论题必须一次锁定

C 项目的写作启动包在 v2.1 时才补上一条：

> "⑦'全文灵魂'位置定死为第三章（二）末尾"

而启动包写完后 **17 分钟**，正文初稿就开始了。也就是说：**核心洞见是在动笔前夕才补进去的**。
后面所有"结论先于证据""逻辑衔接点"的修补，都是在为这个迟到的定锚还债。

A 项目相反：它的核心区分（道德之信 vs 制度之信）在第一版就写在摘要里，
后面四版都是在**深化同一个论题**，而不是寻找论题。

### 检查方法

动笔前问三个问题，任何一个答不上来就不要开写：

1. 全文的**唯一判断**是什么？（必须一句话说得出来）
2. 这个判断在第几章被**论证**，而不是被**宣布**？
3. 每一章对核心论题的**贡献**是什么？（若某章删掉不影响论题，这章就不该存在）

## 四、版本健康度监控

```bash
python scripts/redundancy.py 论文_v1.md 论文_v2.md 论文_v3.md 论文_v4.md
```

输出：

```
==================================================================
版本曲线体检
==================================================================
  论文_v1.md      9871 字             █████████████████████████████
  论文_v2.md     12716 字     +28.8%  █████████████████████████████████████
  论文_v3.md     13712 字      +7.8%  ████████████████████████████████████████
  论文_v4.md      5837 字  -57.4%  ⚠️ 结构塌方嫌疑  █████████████████
```

**判读规则**：

| 曲线形态 | 含义 | 动作 |
|---|---|---|
| 平稳增长（+5% ~ +30%） | 健康，在深化 | 继续 |
| 小幅波动（±5%） | 正常润色 | 继续 |
| **单版跌幅 > 40%** | **结构塌方嫌疑** | **停下，重审论题与章节框架** |
| 连续多版零增长 | 停在原地空转 | 检查是否在做无效补丁 |
| 单调快速增长（>50%） | 注水，可能超字数 | 检查是否在堆砌而非论证 |

## 五、车轱辘话的机械检测

```bash
python scripts/redundancy.py 论文正文_XX.md
```

会报出五类问题：

| 类别 | 含义 |
|---|---|
| ① 近似重复句 | 两句话说的是同一层意思（相似度 ≥ 0.65） |
| ② 超长句 | > 100 字，读者需要断气 |
| ③ 臃肿段落 | > 500 字，一个自然段塞了多层信息 |
| ④ 填充语 | 「值得注意的是」「由此可见」「换言之」等，出现 ≥ 3 次 |
| ⑤ 重复长片段 | ≥ 10 字且出现 ≥ 3 次的片段，几乎必然是复制粘贴残片 |

### ⚠️ 诚实的边界：这个工具不能判断论文好坏

实测对比：A 项目（评价最好）报了 5 处超长句，C 项目（评价最差）只报了 1 处。
原因很简单——**A 是文本分析类论文，长句是它的正常文风**（引原文 + 分析，句长天然偏长）。

所以：

- 工具的用途是**帮你快速定位可疑段落**，省去通读两万字找重复的力气；
- **它不构成质量判断。** 是否要改，由你看上下文决定；
- 排比、递进、内外对照式的**有意重复**是有修辞价值的，不要机械去重；
- 脚注定义行会被自动排除（同一文献在不同脚注出现、页码不同，是正确的）。

## 六、证据纪律：未读的就不能引

B 项目留下了一个可直接照抄的做法——它发现自己引用了 5 部**没有真正读过**的原著
（领导人著作、党章、条例），于是写脚本把这 5 条参考文献连同正文标注一并删除：

```
"""删除未读原著的引用(总书记著作/党章/条例/决定), 重编号, 修正正文标注"""
DROP_PREFIXES = ["[22] 习近平. ...", "[23] 中共中央. ...", "[24] 中国共产党章程", ...]
```

**这是"不虚挂引用"纪律最硬的执行方式：发现自己引了没读的东西，不是补读，而是删掉。**

规则：

1. 引用前确认原文在工作区，且你确实读过相关段落。
2. 只拿到摘要的文献，只能作背景性提及，且标注 `[摘要参考]`。
3. 领导讲话、党内法规、政策文件若未获取全文，**不要凭印象引用**。
4. 删完记得跑 `renumber.py` + `validate.py`。

## 七、自审必须落盘（因为审稿在另一个窗口）

**本工作流的审稿环节在独立窗口中进行，并使用更强的模型。**
理由与操作规程见 `08-self-review.md` 第二节。这里只说它对修订纪律的推论：

### 窗口隔离 → 交接只能靠文件

写作窗口里堆着启动包、精读笔记、每一轮的修改理由；审稿窗口**什么都看不到**。
两边唯一的通道就是文件：

```
审稿窗口 ──落盘──→ 审稿意见_M1.md ──→ 写作窗口执行修订
```

**把意见直接变成 `replace(old, new)` 语句改掉的**——等于把审稿结果销毁了：
改了什么、为什么改、还有哪些没改，全部不可追溯，下一轮也无从对照。

### 因此产生的两条规矩

1. **每一轮自审产出一个 `审稿意见_M<N>.md`**（模板见 `assets/04`），
   写明【位置】【原文】【问题】【具体改法】【依据】。修订时逐条对照执行，改完打勾。
2. **送审前必须清洗稿件**：
   ```bash
   python scripts/mk_review_packet.py 论文正文_XX_v5.md --round 1
   ```
   否则"审稿人"会看到 `> 写作状态：全文初稿 v3·编号定稿`、`# 论文正文_XX（全文 v5）`
   这类内部标记，从而污染它的判断。

> C 项目（被放弃的那个）的审稿修订只体现在 `fix_review.py` 里，
> **没有独立存留的审稿意见报告**。这是它无法追溯、无法复盘的直接原因。

## 八、修订阶段自检清单

- [ ] 本轮修订是否**整段重写**，而不是 `replace()` 打补丁？
- [ ] 新版本是否另存为 `_vN+1`，没有覆盖旧版？
- [ ] 字数曲线是否平稳？（单版跌幅 > 40% 要停下来重审论题）
- [ ] `redundancy.py` 报出的重复句，是**应删的冗余**还是**有意的排比**？
- [ ] 有没有引用了未读原文的文献？（有则删，不要补）
- [ ] 本轮自审意见是否已落盘为 `审稿意见_M<N>.md`？
- [ ] 审稿是否在**独立窗口 + 更强模型**中完成？（不要在同一窗口自审）
- [ ] 送审前是否用 `mk_review_packet.py` 清洗了稿件？
- [ ] 修订后是否重跑了 `renumber.py` + `validate.py`？

---

## 九、一句话总结

> **论文不是"改"出来的，是"重写"出来的。**
> 资料准备得再齐，也救不了一个没锁定论题就开始打补丁的项目。
