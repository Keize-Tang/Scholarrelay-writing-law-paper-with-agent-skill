# 13 · 配套技能协同

> 本工作流不是孤立的。技能库里另有三个技能与本流程互补——
> **它们不被合并进来，而是各司其职。**

## 为什么不合并

| 技能 | 性质 | 为什么不吸收 |
|---|---|---|
| `web-access` | 通用联网基础设施（CDP 直连本地 Chrome） | 体积大、有常驻进程、涉及登录态；属基础设施，应独立安装升级 |
| `browser-use` | 通用浏览器自动化 CLI | 同上，且与 `web-access` 功能重叠，用户可自行择一 |
| `pdfkit-py` | 通用 PDF 工具箱（65 个文件） | 只有"OCR 扫描件"一件事与本流程相关；常规提取已由 `scripts/pdf2txt.py` 覆盖，整体吸收会严重超重 |

**原则**：本流程吸收的是**方法与规范**；工具类技能保持独立，通过"何时调用"的约定协同。

---

## 一、web-access —— 核实事实与文献

**用途**：所有联网操作。CDP 直连本地 Chrome，支持登录态。

### 在本流程中的三个调用点

| 调用点 | 具体任务 |
|---|---|
| **阶段 0 定锚** | 核实法条现行版本；核实政策文件的文号、成文日期、施行日期 |
| **阶段 3 精读** | 微信公众号文章、需登录才能看的页面（用普通抓取会返回空） |
| **阶段 5 修订 / 阶段 8 自审** | 核对案例的编号与裁判要点；核对媒体报道的原始出处与日期 |

### ⚠️ 关键约定：不要用浏览器自动化去打通知网

> **AI 在 webvpn + 知网环境下无法稳定下载全文。所以知网侧的
> 检索、导出题录、下载 PDF 一律由人完成，`web-access` / `browser-use`
> 都不用来替代这一步。**
>
> `web-access` 用于知网**之外**的核实工作。

#### 为什么不去"打通知网"（这个判断很重要）

知网这类机构订阅库的访问控制是**三层叠加**的：

| 层 | 校验什么 |
|---|---|
| ① **IP 授权** | 请求是否来自机构出口 IP（须先连入学校 webvpn） |
| ② **登录态** | 有效会话，绑真实浏览器 cookie，常带设备指纹 |
| ③ **下载额度** | 当日余额，超限即拒且不可预测 |

**这是一个授权问题，不是技术难题。** 硬去做会有三个后果：

1. **不稳定**：额度何时耗尽、何时触发风控都无法预知，流程随时断。
2. **有风险**：部分站点对自动化检测严格，**存在账号被封禁的可能**——
   为了省下用户几十秒，去冒封禁其机构账号的风险，不划算。
3. **门槛反而更高**：要让非专业使用者自己配好常驻进程、CDP 端口、
   登录态保持、验证码人工介入……**这一步比写论文本身还难**，
   正是众多"自动查文献"技能装了却用不起来的原因。

**结论**：把链路切在**授权边界**上。
人持有授权，几十秒做完检索/导出/下载；AI 把算力全部投向
批量阅读、写作与校验——这才是投入产出比最高的分工。

> 详见 `references/01-division-of-labor.md` 与 `02-cnki-export-guide.md` 第零节。

### 注意事项

- 部分站点对自动化检测严格，有账号封禁风险。
- 抓取到的页面内容要**核对权威性**：能用官方来源（政府网、最高法、期刊官网）的，不用媒体转述。
- 媒体来源只能作"舆论认知"材料，**不能作为规范论证依据**（见 `05-writing-discipline.md`）。

## 二、browser-use —— 网页交互与截图

**用途**：需要点击、填写、翻页、截图取证的浏览器操作。

### 在本流程中的调用点

| 调用点 | 具体任务 |
|---|---|
| **阶段 3 精读** | 某些文献放在需要交互才能展开的页面上，需点开获取全文 |
| **事实取证** | 对涉及事实争议的素材做**截图留证**（如宣传物料与正片的视觉对比） |
| **投稿** | 查询投稿系统状态（应由人操作，AI 仅协助） |

### 与 web-access 的选择

两者功能有重叠。简单判据：

- **只需要"读到内容"** → 优先 `web-access`（更轻，尊重登录态）
- **需要"点击／填写／截图"** → 用 `browser-use`

### 注意事项

- `browser-use` 的硬规则：**不得凭记忆编造 URL、页面标题或元素文本**，
  每次交互后必须用 `browser-use state` 或 `screenshot` 验证。
  这条规则与本流程的"证据链闭环"完全一致——**截图取证是有价值的做法**。
- 涉及事实争议的取证（如某部电影的宣传物料），截图要**同时记录获取时间与来源 URL**，
  并在正文中如实标注取证方式。

## 三、pdfkit-py —— 只用于扫描件的 OCR

> ⚠️ **PDF 提文本的常规做法在本流程内，不在 pdfkit-py。**
> 常规提取请用 `python scripts/pdf2txt.py 文献目录/`（见 `14-pdf-to-text.md`，
> 已实测选型、无需重新评估）。**pdfkit-py 只承担一件本流程做不了的事：OCR 扫描件。**

### 用途：处理没有文本层的 PDF

`pdf2txt.py` 会按每页平均字符数自动判定扫描版并报出来。这类文件需要用 OCR 转换：

```bash
# 概念示意，具体命令见 pdfkit-py 自身文档
pdfkit ... 对扫描版 PDF 做 OCR
```

### 为什么不用它做常规提取

| | `scripts/pdf2txt.py`（本流程） | pdfkit-py |
|---|---|---|
| 依赖 | 本机已装 PyMuPDF，**零安装** | 需先执行其环境初始化脚本 |
| 批量 | 一条命令处理整个目录 | 需逐个调用 |
| 增量 | 自动跳过已提取的 | 无 |
| 扫描版判定 | **自动**（每页字符数） | 需人工判断 |
| 适用 | 常规提取（99% 的情况） | OCR 扫描件（少数情况） |

**一句话**：常规用 `pdf2txt.py`；`pdf2txt.py` 报"需 OCR"时，才动 pdfkit-py。

### 提取出文本之后

txt 是工作底本，用于**回读原文核验**（见 `05-writing-discipline.md`）。
注意两点：

1. txt 中的 `PAGE n` 是 **PDF 页序**，不一定是刊物页码——精读笔记标页码时要写明是哪一种。
2. **OCR 结果必须人工抽查**：数字、年份、文献编号、页码最容易识别错
   （把「2024」识成「202A」这类错误进了正文就是硬伤）。

### 边界

`pdfkit-py` **不承担**论文写作、润色、排版咨询——
**这些是本工作流 `07-docx-formatting.md` 与 `scripts/md2docx.py` 的职责**。
不要把"内容创作 + 投放 PDF"的复合任务交给它。

## 四、调用关系总表

```
阶段 0 定锚    ──→ web-access（核实法条/政策文件）
阶段 1 题录    ──→ 人操作（知网，AI 不介入）
阶段 2 分级    ──→ 本流程 scripts/parse_cnki.py
阶段 3 精读    ──→ scripts/pdf2txt.py（提取 PDF 文本，本流程内，零安装）
                  pdfkit-py（仅当报"需 OCR"时，处理扫描件）
                  web-access（登录态页面 / 微信文章）
                  browser-use（需交互的页面 / 截图取证）
阶段 4 写作    ──→ 本流程 references/
阶段 5 修订    ──→ 本流程 scripts/redundancy.py + scripts/aitrace.py
阶段 6 校验    ──→ 本流程 scripts/validate.py + renumber.py + cnki2gbt.py
阶段 7 排版    ──→ 本流程 scripts/md2docx.py
阶段 8 自审    ──→ 本流程 references/08 + 12
                  web-access（核对事实）
阶段 9 投递    ──→ 人操作
```

## 五、环境与依赖

| 技能 | 依赖 | 备注 |
|---|---|---|
| 本流程 7 个脚本 | Python 3.9+ 标准库 | 无需安装任何包 |
| `scripts/pdf2txt.py` | **PyMuPDF**（本机已装，零安装）；无则回退 pypdf | `pip install pymupdf` |

| `browser-use` | `browser-use` CLI | 需先跑 `browser-use doctor` |
| `pdfkit-py` | 见其自身 SKILL.md | 首次使用需执行其环境初始化脚本 |
